# vramfit

**下载一个模型之前，花两秒看看它在你电脑上跑不跑得动。**

<sub>by [RoRoToCode](https://www.roroto.com) · MIT · 命令行与网页共用同一份推算代码</sub>

> **在线体验**：<https://www.roroto.com/vramfit> —— 不用装任何东西，打开网页贴个链接就有结果，
> 模型文件不出浏览器。想批量查、想扫本地目录，再用下面的命令行。

把 `.gguf` 拖进来，或者贴一个 Hugging Face 链接。它读文件头里那几十 KB 元数据
（层数、注意力头、量化档位、对话模板），结合你的显卡算一遍，然后告诉你：

- 装不装得下，能开多大的上下文
- 大约每秒吐几个 token
- 能不能直接当 coding agent 用

不下载模型、不写硬盘、不动你的配置。一个 15 GB 的文件，只读前面几十 KB。

```bash
npx vramfit unsloth/Qwen3-8B-GGUF
```

（克隆下来跑的写法是 `node check.mjs ...`，参数完全一样。）

```
  ═══════════════════════════════════════════════════════
  GGUF 体检报告
  ═══════════════════════════════════════════════════════

  ✓ 可以当 coding agent 用
    32K 上下文装得下，模板也能驱动工具调用

    ⚠ 静态推算，仅供参考；实际加载运行一次才算数
```

## 先说清楚它不做什么

- **不是下载器** —— 查完你自己去下，它不占你的带宽。
- **不是跑分** —— 速度按显存带宽估，不是实测，差个两三成很正常。
- **不替你做决定** —— 它只把「根本跑不动」的排掉，选哪个还是看你。
- **结论都只是参考** —— 真正的答案永远在你自己加载一次之后。
- **现在只读 GGUF。** safetensors / MLX 还没支持，贴上去会直接告诉你格式不认识，
  不会硬猜一个数出来。原因和进度写在下面的「格式支持」里。

**关于名字**：`vram` 在这里泛指「能分给模型的那部分内存」—— 独显的显存、
Apple Silicon 的统一内存、核显的共享内存，算的是同一件事；`fit` 就是装不装得下。
所以 Mac 上照样能用，报告里会写成「可用作显存 21.33 GB」，而不是硬叫它 VRAM。

**这是一个命令行工具**，需要 Node 18+，没有任何依赖。
Windows 下双击 `check.cmd` 就行，不用记参数。

**不想装 Node？** 用网页版：<https://www.roroto.com/vramfit> —— 贴个链接就出结果，
文件不出浏览器。网页版源码也在本仓库的 `site/`，构建时复用根目录的 `core/` 和 `net/`，
不随 npm 包发布。

English: [README.en.md](README.en.md)

## 用法

|  | 网页版（roroto.com/vramfit） | 命令行（本仓库） |
|---|---|---|
| 装东西 | 不需要 | 需要 Node 18+ |
| 贴 HF 链接 | ✅ | ✅ |
| 拖本地 `.gguf` | ✅ 文件不出浏览器 | ✅ |
| 递归扫整个目录 | ❌ | ✅ |

## 语言

界面默认跟随系统：中文环境给中文，英文环境给英文。想固定一种，用 `--lang`：

```bash
vramfit --lang en model.gguf     # 强制英文
vramfit --lang zh model.gguf     # 强制中文
```

```bash
VRAMFIT_LANG=en vramfit model.gguf     # 设一次，整个终端会话都生效
```

Windows 下可以 `set VRAMFIT_LANG=en` 再双击 `check.cmd`。

**在交互模式里随时换。** 不用退出重开，`检查 >` 提示符后面直接敲：

```text
检查 > lang            → 报当前语言，顺手给出用法
检查 > lang en         → 立刻切成英文（提示符变成 check >）
检查 > lang zh         → 切回中文
检查 > en  /  cn  /  -en   → 也行，敲两个字母就够
```

切换只回一行提示，**不清屏**——你敲 `lang` 的时候屏幕上往往正放着一份刚跑完的报告，
顺手把它抹掉等于为了改语言惩罚用户。清屏是 `cls` 的活。提示符自己会变成 `check >`，
这就是最直接的确认。`lang` 后面认 zh / en（含 `cn`、`中文`、`english` 这些写法），
乱写的词不动当前语言，只回一句提示。

命令行那边 `--lang` 是严格的，只认 `zh*` / `en*`：脚本里拼错了就该当场报错，
猜只会把 bug 藏起来。交互模式是给人敲的，所以宽一些。

**为什么不并排显示。** 报告是栅格排版的，标签列 12 个显示宽度；中英并排（"文件 File"）
会把它撑到 20 列以上，窄终端直接折行，整张表就散了。所以只显示一种语言，由你选。

几条界线：

- **术语不翻。** GGUF、KV cache、Q4_K_M、tok/s、Metal 这些翻了反而看不懂。
- **数字和单位不本地化。** 全局都是 `12.34 GB`，不做 GB / GiB 之分。
- **`--json` 不跟语言走。** 里面的 `verdict` 是稳定标识（`agent-ready` 等），
  翻译会直接打断下游脚本；同一份输入在任何机器上都要输出逐字节相同的结果。
- **`--ascii`** 把 `✓ △ ✗ █ ░ ═` 换成 `+ ~ x # - =`，给老终端和重定向到日志时用。

网页版目前只有中文（它和命令行共用判定逻辑，但页面文案还没接进词条表）。

## 快速开始

### 先确认有 Node

这个工具是纯 JS 写的，**必须有 Node.js 18+ 才能跑**，没有别的运行方式：

```bash
node --version        # 需要 v18.0.0 或更高
```

没有的话，Windows 一条命令装好：

```bash
winget install OpenJS.NodeJS.LTS
```

或者去 <https://nodejs.org/> 下 LTS 安装包。版本太老会在启动第一行就提示升级，
不会跑到一半报 `fetch is not defined` 这种看不出原因的错。

**不想装任何东西**：用网页版 <https://www.roroto.com/vramfit>。代价是不能递归扫目录、
不能读实测显存、没有 `--json`。

### 方式零：装成一个命令（可选）

```bash
npm i -g vramfit      # 之后直接：vramfit 链接或文件
```

不装也完全可以 —— 克隆下来 `node check.mjs` 参数完全一样，只是命令长一点。
下面三种方式的写法都按 `vramfit` 写，把 `vramfit` 换成 `node check.mjs` 同样成立。

### 方式一：交互模式（最省事）

Windows 下**双击 `check.cmd`**，出现提示后把链接粘贴进去，回车即出报告：

```
  检查 > https://hf-mirror.com/unsloth/Qwen3-8B-GGUF
  检查 > D:\models\qwen3-8b-q4_k_m.gguf
  检查 > unsloth/Qwen3-8B-GGUF
  检查 > q
```

粘贴方式：**`Ctrl+V` 或右键**（cmd 窗口默认右键即粘贴）。一次可以粘多条，用空格或换行隔开。从浏览器地址栏、微信、飞书复制过来的链接常带零宽字符、中文引号、句末句号，这些会自动清掉，不用手动修。

万一某个窗口怎么粘都粘不进去（旧版 conhost、安全软件接管键盘），输入 `paste` 回车，直接从系统剪贴板读，绕开终端。

命令行等价写法：

```bash
node check.mjs
```

| 粘什么 | 会发生什么 |
|---|---|
| `.gguf` 文件直链 | 体检这一个文件 |
| 模型主页（`/owner/repo`） | 自动转成量化对比，列出全部变体 |
| `blob` 页面地址 | 自动换成文件直链 |
| 本地 `.gguf` 路径或目录 | 体检 / 递归扫整个目录 |
| `owner/repo` | 同模型主页 |

命令：`help` 看参数、`paste` 从剪贴板取内容、`cls` 清屏、`q` 退出。

### 方式二：拖拽

把 `.gguf` 文件（可多选）或它所在的目录拖到 `check.cmd` 图标上。

**网址不能这样拖**，原因跟链接本身无关：`cmd.exe` 把 `&` 当命令分隔符，`https://host/x.gguf?a=1&b=2` 拖进去会从 `&` 处断开，后半截被当成一条命令执行。带 `&` 的链接请双击 `check.cmd` 粘到窗口里，或用引号包住：

```cmd
check.cmd "https://host/x.gguf?download=true&rev=1"
```

### 方式三：一行命令

```bash
node check.mjs model.gguf
node check.mjs models/              # 递归扫目录里所有 .gguf
node check.mjs models/*.gguf        # 批量
node check.mjs --json models/       # 机器可读，可直接进 CI
```

**不用下载也能查**——贴链接，只读文件头部（约 10–25 MB），不拉整个模型：

```bash
node check.mjs https://hf-mirror.com/unsloth/Qwen3-8B-GGUF/resolve/main/Qwen3-8B-Q4_K_M.gguf
node check.mjs https://huggingface.co/unsloth/Qwen3-8B-GGUF/resolve/main/Qwen3-8B-Q4_K_M.gguf
```

huggingface.co 和 hf-mirror.com **两种域名都认**：
- 贴 `huggingface.co` 会自动换成国内镜像；镜像不通时再退回官方源
- 贴 `hf-mirror.com` 直接用，不用改
- 模型主页链接会自动变成"量化对比"，不用手动拼 `resolve/main/xxx.gguf`

**对比一个仓库里的全部量化**，直接回答"我该下哪个"：

```bash
node check.mjs --repo unsloth/Qwen3-8B-GGUF
node check.mjs https://hf-mirror.com/unsloth/Qwen3-8B-GGUF    # 等价写法
```

目录会自动递归展开——LM Studio 的模型放在 `models/<publisher>/<repo>/x.gguf`，传上层目录即可全扫。

| 选项 | 作用 |
|---|---|
| `--repo owner/name` | 列出一个 HF 仓库的全部量化并逐个远程体检 |
| `-i, --interactive` | 兼容保留：不带任何参数时已经自动进入交互模式 |
| `--kv <类型>` | KV cache 精度：`f16`（默认）/ `q8_0`（省一半显存）/ `q4_0` |
| `--vram 12` | 假设有 12 GB 显存（保留本机卡名和带宽，只换容量），用于评估"换卡值不值" |
| `--mirror <地址>` | 换模型站点。默认 `hf-mirror.com`；写 `https://huggingface.co` 就是直连官方 |
| `--lang zh\|en` | 界面语言。默认跟随系统，也可以用 `VRAMFIT_LANG` 环境变量 |
| `--about` | 打印全部参数与假设 —— 这份报告到底是怎么算出来的 |
| `--no-color` | 关闭颜色（重定向时自动关闭） |
| `--ascii` | 用 ASCII 符号代替 `✓ △ ✗ █ ░`，给老终端和日志文件 |
| `-v, --version` | 版本号 + 仓库地址（二次分发时用户能查到出处） |

参数写错会直接报错并返回退出码 1，不会静默回落到默认值。`--kv=q8_0` 这种等号写法也认。

默认走镜像，是因为国内直连 `huggingface.co` 经常超时，而镜像只是把同一份文件转出来，
路径和内容都一样。海外用户、或者镜像出问题时，用 `--mirror https://huggingface.co` 直连官方；
想长期换掉，设环境变量 `VRAMFIT_MIRROR` 就行。

每份报告末尾都带一段「参数与假设」，就地写清权重、KV、上限、速度各自是按什么算的；
`--about` 是它的完整版，和网页上那个可展开面板是同一份内容。

## 平台支持

Windows / Linux / macOS 都能跑，只是显存的问法各不相同：

| 平台 | 显存来源 | 预算上限怎么算 |
|---|---|---|
| Windows + NVIDIA | `nvidia-smi`，失败退注册表 | 总显存 × 94%（WDDM 能驱逐别人的显存） |
| Windows + AMD | `rocm-smi`，退注册表 | 同上 |
| Linux + NVIDIA | `nvidia-smi` | **当前可用 × 92%**（显存不可驱逐） |
| Linux + AMD | `rocm-smi`，退 `/sys/class/drm/*/mem_info_vram_*`（无需装 ROCm） | 同上 |
| macOS（Apple Silicon） | `sysctl hw.memsize`，按 Metal 建议工作集 | 建议工作集 × 90%（统一内存，与系统共享） |
| 都没有 / 驱动没装 | 退化成 CPU 推理 | 物理内存 × 80% |

核显（Intel / AMD APU）按共享内存的一半估算，并且在同时有独显时不会被选中。预算上限那一行会写明当前用的是哪套算法。

**退出码**：有文件读不到（或仓库里一个变体都读不到）时返回 1，正常为 0。`--json` 配合退出码可以直接进 CI。

## 格式支持

| 格式 | 状态 | 说明 |
|---|---|---|
| **GGUF** | 支持 | 含分片（只算第 1 片 × 片数）、自动跳过 `mmproj` 视觉投影、量化档位和对话模板都从元数据读 |
| safetensors | 未支持 | 超参在 `config.json` 里而不在权重里，且要先决定转成哪个量化档位才有意义 |
| MLX | 未支持 | 本质是 safetensors + `config.json` 里的 `quantization.bits` |

后两种不是解析不了，而是**结论的口径不一样**：GGUF 的体积就是它跑起来的样子，
safetensors 的体积是 bf16 原文件，得先说"转成 Q4_K_M 之后约 4.6 GB"才谈得上装不装得下。
这一层没想清楚之前先不做，免得给出一个看着精确、其实答非所问的数字。

贴一个不认识的格式进来，它会明确说「这个直链不是 .gguf 文件」，不会硬算。

## 和网页版的关系

网页版源码在仓库的 `site/` 目录，构建时直接读根目录的 `core/` + `net/`，
部署在 <https://www.roroto.com/vramfit>。npm 包里不含 `site/` —— 装命令行的人不会多下网页。

两边共用的只有两处，都是纯计算、不含 IO：

- `core/` —— GGUF 解析、KV 推算、显存预算、量化判定
- `net/` —— HTTP Range 读取 + HF 仓库列表

网页版在这个仓库的 `site/` 目录里，构建时直接从根目录读这两个目录，不复制、不改写，
所以两边数字永远一致。

代价是一个约束：`site/` 必须是仓库根的直接子目录，否则 `node site/build.mjs` 找不到
`core/`。命令行完全不受影响 —— `npx vramfit` 装的只是根目录那些文件，没有 `site/`。

## 项目结构

```
core/          纯计算：GGUF 解析、KV 推算、显存预算、量化判定。不含任何 IO
core/assumptions.mjs  全部参数与假设的唯一来源（报告 / --about / README / 网页共用）
core/i18n.mjs  全部界面文案的中英词条（报告 / --about / 参数报错 / 网页共用）
net/           HTTP Range 读取 + HF 仓库列表。只用 fetch，Node 和浏览器共用
cli/           本机硬件探测（nvidia-smi / rocm-smi / sysctl），Node 专属
check.mjs      命令行入口：参数解析、交互循环、ANSI 报告
check.cmd      Windows 双击启动（探测代理支持、透传退出码）
test.mjs       命令行侧测试
site/          网页版（纯静态）。构建时从根目录读 core/ + net/，不复制
```

`core/` 和 `net/` 要保持能在浏览器里跑（网页版直接引用），所以不许出现 `node:` 模块 ——
`npm test` 和 CI 都守着这条线。

## 为什么值得先查一下

本地跑小模型翻车，几乎都翻在同一个地方：**模型加载起来了，但 agent 用不了。**

- 模型没有 `chat_template` → 一问一答变成"接着往下写"
- 模板里没有 `tools` 分支 → Claude Code / Cline 发了工具定义，模型看不懂
- 宣称 256K 上下文，实际 8G 卡只能开 32K
- 好不容易开起来，KV cache 把显存吃满，桌面开始卡

这几种情况在下载前都看不出来。`vramfit` 读完几十 KB 的元数据就能给结论，
不用等 5 GB 下完、加载失败、再换一个。

## 报告长什么样

```
    开销        固定 200 MiB
    KV          ctx × 层数 × n_kv_head × (k+v) × 每元素 2 B
    上限        Windows WDDM：max(可用×0.92, 总显存×0.94)
    速度        带宽 × 0.7 ÷ 权重GB，误差 ±15%
    门槛        需要量 > 上限×0.85 算「接近」；< 3.00B 只算能跑；< 8K 算太短
    完整清单    --about
```

关键信息不是「能跑」，而是 **「模型原生支持 128K，但你这台机器只能开到 32K」** ——
这才是真正影响使用的那个数字。

## 实测校准

这个工具的显存模型是在真机上对着 llama.cpp 校准过的（RTX 2080 8G / `Ornith-1.5-9B-Q4_K_M` / `-ngl 99`），四个档位全部实际拉起服务并测速：

| 上下文 | 工具预测 | 实测显存 | 误差 | 实测速度 |
|---|---|---|---|---|
| 8K | 5969 MiB | 5875 MiB | +1.6% | 52.7 tok/s |
| 16K | 6226 MiB | 6119 MiB | +1.7% | 51.1 tok/s |
| 32K | 6738 MiB | 6676 MiB | +0.9% | 53.9 tok/s |
| 64K | 7762 MiB | 7737 MiB | +0.3% | 57.1 tok/s |

预测一律略高于实测（宁可保守），误差都在 2% 以内。

**64K 那一档被判为 ✗ 是刻意的**：它实测能起来（7737 MiB），但只剩 251 MiB 余量，开个浏览器就会 OOM。工具的立场是"推荐你敢放心用的配置"，不是"极限能塞进去的最大值"。

## 哪些是读到的，哪些是算出来的

报告里严格区分，不允许含糊：

| 项目 | 来源 | 可信度 |
|---|---|---|
| 架构、参数量、量化、层数、head 数、原生上下文 | GGUF 元数据原文 | **实测** |
| `chat_template` 是否存在、是否含 `tools` 分支 | 读模板字符串原文 | **实测** |
| 权重显存占用 | 文件体积（分片按片数折算） | **实测**（GGUF 里权重占绝大部分） |
| 4K–256K 各档能否装下 | 层数 × KV head × head_dim × 精度 | **推算**，真机校准误差 <2% |
| 混合架构的 `full_attention_interval` | 元数据缺失时按 `ssm.*` 推断 1/4 | **推断**，报告里标注 |
| 滑窗架构的层分配比例 | llama.cpp 的架构规则（gemma3 每 6 层 1 层 global） | **推断**，±25% |
| 生成速度 | 显存带宽 ÷ 权重体积 × 效率系数 | **推算**，2 GB 以上模型误差约 1%；更小的模型受固定开销压制，只给上限 |
| 显存带宽 | 内置规格表匹配卡名 | **静态数据**，卡不在表里就不给速度 |
| 量化质量分级（"别用 / 勉强 / 推荐"） | 领域经验，非计算 | **经验判断**，阈值为 agent 场景设定 |
| 是否真能稳定驱动工具调用 | 只看模板 | **推断**，必须实跑一次确认 |
| 参数量是否够做 agent | 一条硬门槛：小于 3B 直接判"太小" | **经验判断** |

## 速度预估

每吐一个 token，要把全部权重从显存读一遍——所以生成速度的瓶颈是**显存带宽**，不是算力。公式就一行：

```
tok/s ≈ 带宽(GB/s) × 效率 ÷ 权重体积(GB)
```

用 RTX 2080（448 GB/s）+ 9B Q4_K_M（5.78 GB）校准：`448 × 0.7 ÷ 5.78 = 54.3`，**实测 53.9**。效率系数 0.7 就是在这里定下来的。

几处刻意的取舍：

- **权重装不下时改按系统内存带宽算**（约 60 GB/s），所以会看到"~6 tok/s"这种数字——那是真实的，部分 offload 就是这个体验。
- **权重小于 2 GB 时只给 200 tok/s 上限，不给具体数字**：0.6B Q4 在 RTX 3050 上公式算出 395，实测 70–120 —— 每 token 的 kernel launch、采样、传输是固定开销，公式在这个量级没有意义。
- **MoE 模型会偏低**：公式按整体体积算，实际只激活一部分专家，真实速度更高，报告里会标注。
- **卡不在内置表里就不给速度**，而不是瞎猜一个数。

## 架构差异已自动处理

几种架构差异已经处理，不需要你手动判断：

- **混合线性注意力**（Mamba / Gated DeltaNet，如 qwen3next / Qwen3-Next）：每 N 层只有 1 层带 KV，其余是线性注意力。优先读 `full_attention_interval`；**元数据没写这个键时，看 `ssm.*` 参数是否在场来判定**，按 3 层线性 + 1 层全注意力推断，并在报告里注明"推断"。不处理会把 KV 高估 4 倍。
- **滑窗注意力**（`sliding_window`，如 Gemma 3/4）：滑窗层只保留最近 N 个 token。只要元数据里有 `sliding_window` 就走滑窗分支，缺 `key_length_swa` 时用 `key_length` 顶替 head_dim，报告里会写明。旧版只认 `key_length_swa`，导致 Gemma 3 的滑窗分支从不生效、128K 被算成 19 GB。
- **MTP 层**（`nextn_predict_layers`）：llama.cpp 会忽略，不计入推理层数。
- **分片模型**（`…-00001-of-00004.gguf`）：体积按「第 1 片 × 片数」折算，指向第 2 片之后会直接提示改指第 1 片。
- **原生上下文是硬边界**：超出它的档位一律标 ⚠，不计入建议值——RoPE 外推在短对话里看不出来，跑长任务时会崩。

两条已知偏差，会直接印在报告里：滑窗架构的层分配比例是按架构规则推断的（±25%）；Windows 上"预算上限"含可驱逐的显存（关掉 LM Studio / 浏览器能释放），Linux / macOS 上不含，报告里那句话会跟着平台变。

## 它不做什么

- **不下载模型。** 本地文件只读头部；远程地址用 HTTP Range 只取需要的几段（通常 10–25 MB），不会把 5 GB 拉下来。不上传你的任何文件，不注册，不收集数据。
- **不做模型管理。** 不启动服务、不切换模型、不管端口。那是 Ollama / LM Studio / llama-swap 的活。
- **不替代实跑。** 模板里写了 `tools` 不等于模型真会用。它负责排掉"根本不可能"的选项。
- **不判断模型聪不聪明。** IQ1 被判"别用"是因为低比特量化输出本身不稳定，不是因为模型能力差。唯一的例外是"小于 3B 直接判太小"这条硬门槛，只用来拦掉明显不可能驱动 agent 的档位。

## 免责声明与参数说明

**先说结论：所有数字都是静态推算，不是实测。** 这个工具不加载模型、不跑推理、
不测真实吞吐 —— 它只把 GGUF 头部元数据读出来，套一套硬件规格做算术。
它负责排掉"根本不可能"的选项，不负责发合格证。

参数全部集中在 [`core/assumptions.mjs`](core/assumptions.mjs)。命令行的报告、
`--about`、网页上那个可展开面板、以及下面这张表，渲染的都是同一份常量 ——
不会出现"文档说 200 MiB、代码按 400 MiB 算"这种最难查的问题。

| 环节 | 怎么算 | 前提与误差 |
|---|---|---|
| **权重体积** | 文件字节数 | 分片模型按「第 1 片 × 片数」估算（各片大小基本相等）；含 embedding / lm_head |
| **KV cache** | `ctx × 层数 × n_kv_head × (k_dim + v_dim) × 每元素字节` | f16 = 2 B、q8_0 = 1.0625 B、q4_0 = 0.5625 B（后两者带 per-block scale） |
| **混合线性架构** | 只算 1/N 层有 KV | N 读 `full_attention_interval`；缺失时按 `ssm.*` 参数推断为 4（这是推断，报告里会标出来） |
| **滑窗架构** | full 层按 ctx，其余层只保留最近一个窗口 | 层分配比例按架构规则推断，**±25% 偏差** |
| **运行时开销** | 固定 200 MiB | batch 与计算缓冲。RTX 2080 + 9B Q4_K_M 实测约 80 MiB，这里留了余量 |
| **显存上限（Windows）** | `max(可用 × 0.92, 总显存 × 0.94)` | WDDM 允许驱逐其他进程占用的显存 |
| **显存上限（Linux）** | `可用 × 0.92` | 显存不可驱逐，只能按当前可用算 |
| **显存上限（macOS）** | Metal 建议工作集 × 0.9 | 读不到建议工作集时按物理内存 75% |
| **没有独显** | 物理内存 × 0.8 | CPU 推理，要给系统和页缓存留空间 |
| **生成速度** | `带宽 × 0.7 ÷ 权重GB` | **±15%**；不含首字延迟；小模型受固定开销压制，2 GB 以下最多报 400 tok/s |
| **MoE** | 未计入激活比例 | 每 token 只读部分专家，实际速度会**高于**估算 |

判定门槛（也都在上面那个文件里）：

- 需要量 > 上限 **× 0.85** → 标"接近上限"，仍算装得下，但再往上开就会失败
- 参数量 **< 3B** → 只算"能跑"，不算 agent 可用。这不是能力评测，只是拦住明显不可能的档位
- 上下文 **< 8K** → 判"太短"，塞不下一个像样的代码文件
- 量化 **1–2 bit** → 判"别用"。这是**经验分级，不是测出来的**；省下的显存会以工具调用反复失败的形式还回来

明确不做的判断：

- **不实测吞吐**，不测首字延迟，不测并发
- **不读真实显存占用**（网页端做不到，浏览器不暴露；只有网页版的"已占用"是让你手填的）
- **不处理多卡**：只看第一块显卡，多卡切分 / 张量并行不在估算范围
- **模板只做字符串特征分析**：有 `tools` 分支 ≠ 模型真会稳定调用工具

所以：**报告能告诉你"这个组合大概率不行"，但不能告诉你"这个组合一定行"。**
决定下载 20 GB 之前，值得花五分钟实际跑一次。

## 常见问题

**Q：没有独立显卡能用吗？**
能。会按 CPU 推理估算——只用物理内存（按 80% 计），速度按内存带宽算，报告里会写"CPU 推理"。这个速度做 agent 基本不可用，但"能不能装下、模板是否支持工具"这些结论仍然有效。

**Q：AMD / Intel 显卡？**
显存靠注册表读取，能给容量判断。但 llama.cpp 对 AMD 要走 Vulkan/ROCm，实际可用显存和速度有出入，报告里后端会标 Vulkan。

**Q：为什么建议上下文比模型宣称的小这么多？**
KV cache 随上下文增长。9B 纯注意力模型开 64K，KV 就要 4 GB 以上，8G 卡装不下。厂商宣传的"支持 256K"通常指 24G 以上显卡。

**Q：和其他模型管理器冲突吗？**
不冲突，它只读不写。但如果你开着 LM Studio / Ollama 占了几 GB，报告会提示——关掉它们再跑，可用显存会多出来。

**Q：在 PowerShell 里重定向出乱码？**
PowerShell 5.1 默认按 GBK 解码，先执行 `[Console]::OutputEncoding = [System.Text.Encoding]::UTF8`。

**Q：双击 `check.cmd` 打开窗口后，Ctrl+V / 右键粘贴网址没反应？**
已修。原因是交互模式用 Node 的 `readline` 时会把控制台切进 raw 模式，而 Windows 的 raw 模式会把输入模式改成 `ENABLE_WINDOW_INPUT|ENABLE_VIRTUAL_TERMINAL_INPUT`（实测 `0x0208`），连带清掉 `ENABLE_QUICK_EDIT_MODE` —— conhost 的粘贴正是靠这个标志工作的，于是经典控制台窗口里怎么粘都没反应（Windows Terminal 不受影响，粘贴由终端自己处理）。现在 Windows 上改用「熟模式」，由控制台负责回显和粘贴，实测 `ENABLE_QUICK_EDIT_MODE` 保持开启。

如果你用的还是旧版本，或者窗口仍粘不进去：输入 `paste` 回车，直接从系统剪贴板读，完全绕开终端。

**Q：粘贴的链接提示"没认出这是链接还是文件"？**
按这三点排查：
- 域名只认 `huggingface.co`、`hf-mirror.com`、`hf-mirror.net`。ModelScope、GitHub、网盘链接都不行，会明确提示。
- 复制时带的零宽字符、中文引号、句末句号、`&amp;` 已经会自动清理；如果还不行，看看链接里有没有夹中文说明或空格。
- 报的是"网络连不上 / 请求超时"而不是"没认出"，说明链接已经识别成功，卡在取文件头部——那是镜像此刻不通，等 1–2 分钟再来。

**Q：拖网址到 `check.cmd` 图标上没反应，或报"xxx 不是内部或外部命令"？**
链接里带 `&` 时会被 `cmd.exe` 截断（它把 `&` 当命令分隔符）。改成双击 `check.cmd` 粘到窗口里，或用引号包住整条链接。

**Q：hf-mirror.com 上的模型能验吗？**
能，而且不用改链接，直接粘。工具认这几种写法：

| 粘的地址 | 处理方式 |
|---|---|
| `.../resolve/main/xxx.gguf` | 体检这一个文件 |
| `.../blob/main/xxx.gguf` | 自动换成 `resolve` 直链 |
| `.../owner/repo`（模型主页） | 列出全部量化，一张表对比 |
| `.../tree/main` 等目录页 | 同上，按仓库处理 |
| `owner/repo` | 同上 |

只有 HTML 页面是验不了的（它返回的是网页不是模型），所以工具会自动把主页链接转成能用的形式，而不是报错。

**Q：报"网络连不上"或"拿不到文件大小"？**
两种原因，报告里会分开说：
- **不是文件直链**（比如贴成了 README、safetensors）→ 换成 `.gguf` 直链或模型主页
- **镜像不通** → hf-mirror 会按出口 IP 限流，撞上了就等 1–2 分钟；工具会自动重试并尝试退回官方源，还不行就先下载到本地再查

**Q：为什么远程体检有时要几十秒？**
远程只读文件头部，但 GGUF 的元数据排在词表之后，Qwen 这类十几万词条的模型要读 10–25 MB 才能拿到 `chat_template`。镜像快时 5 秒内，被限流时会慢很多。

**Q：报告说"有模板但不支持工具"，和"无模板"有什么区别？**
两件完全不同的事：**无模板**是模型没带对话格式（会退化成"接着往下写"），**不支持工具**是模板存在但没有 `tools` 分支（能对话，但 agent 塞不进工具定义）。后者可以靠 `--chat-template` 或换 agent 的文本工具协议兜底，前者基本没法用。

**Q：为什么 0.6B 的模型模板和显存都合格，还说不能做 agent？**
因为有一条硬门槛：参数量小于 3B 直接判"能跑，但模型太小"。多轮工具调用对模型能力要求很高，这个量级基本会在第一轮就跑飞。这条不是能力评测，只是拦掉明显不可能的档位——3B 以上仍然要实跑验证。

**Q：分片模型（`-00001-of-00004.gguf`）怎么查？**
指第 1 片就行，体积会自动按片数折算（`第 1 片 × 片数`）。指到第 2 片之后会直接提示改指第 1 片——后续分片里没有元数据，读了只会得到"magic 不匹配"这种莫名其妙的报错。

**Q：速度那一栏为什么写"~200 tok/s 以内"而不是具体数字？**
权重小于 2 GB 时，带宽已经不是瓶颈，每 token 的 kernel launch、采样、传输这些固定开销占主导，公式会算出 400 这种不可能的数（0.6B Q4 在 RTX 3050 上公式给 395，实测 70–120）。这时只给上限，不给假精度。

只嵌 `core/`（或 `core/` + `net/`）也一样：这两个目录独立，不依赖 `cli/` 和 `check.mjs`，
网页版就是这么用的。

**不是法律条款、但希望你遵守的两件事：**

- **别用这个项目的名字做背书。** 包一层 UI 之后叫"官方 vramfit"、或者在小红书/知乎上
  说"作者推荐"，会让用户以为是我发的。改名、注明"基于 vramfit"都可以。
- **把免责声明一起给出去。** 报告里的数字是静态推算，不是实测。你把它展示给用户时，
  那句"仅供参考、需实际加载运行验证"得跟着走。这不是许可证要求，是产品责任——
  用户按你的结论买了 20 GB 的模型跑不动，找的是你不是我。

许可之外还有一层：**工具输出的数字不受版权保护**，你可以随便引用、二次加工；
但那是数据，不是许可证授予的权利，准确性由用的人自己判断。
